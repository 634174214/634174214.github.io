1、首页、列表页中的 标签聚合 目前还是使用PHP渲染的方式，后面有时间可以考虑改为使用JSON，tags在sitenav.json中

2、目前导航、推荐、我的信息都是使用JSON获取，因为从首页跳转到列表、详情页等 依然会有加载等待时间，可以考虑在第一次加载后将
静态json数据存储在localstorage或者sessionStorage中，这样 同域名下其他页面可以不用等待即可获取导航等的内容，实现从缓存加载。
但是注意，以下是咨询AI的回复，仅记录，有空再弄。
----------------------------------------------------------------------
1. 先认清：浏览器其实已经在帮你「缓存」了

  静态 .json 走 HTTP 访问时，浏览器本来就有一层 HTTP 缓存（ETag /
  Cache-Control）。所以你现在「点进列表页还有个请求过程」，很可能不是「每次都完整拉一遍」，而是「缓存命中 / 304
  重验证」——GitHub Pages 对静态文件的 max-age 比较短（我记得是 10
  分钟），所以超过这个窗口就会重新验证一下，但那次验证也很轻（几十毫秒，CDN 就近）。

  也就是说，sessionStorage 相对 HTTP 缓存的增量收益，只是省掉那一次 304
  往返，不是「从每次都请求」变「完全本地」。如果你感觉慢，一半原因其实是
  FOUC（导航那块在等请求回来才渲染，有一瞬间空白），而不是网络本身慢。

  2. 最大的坑：过期导航

  sessionStorage 在一个 tab 的整个生命周期里都有效。如果你改了频道、重生成 sitenav.json，但用户还开着那个
  tab，他看到的导航就是旧的，直到关掉 tab。

  解法只有一个，而且你已经有现成套路：用版本号做 key。比如给 sitenav.json 引用加 ?t=N，缓存时用「完整 URL（含
  ?t=）」当 key，改频道就 +1，旧缓存自动失效。不做这步，缓存就是给自己埋雷。

  3. sessionStorage 还是 localStorage？——你这个场景我建议 localStorage

  关键点：你的导航链接和文章链接都是 target="_blank" 新开 tab。而：

  - sessionStorage 是「每个 tab 一份」，新开 tab 时只是从 opener 复制一份过去，之后各 tab 独立；
  - localStorage 是「同源所有 tab 共享」，首拉一次、全局受益。

  所以对你这种「大量 _blank 新开页」的浏览流，localStorage 更契合——否则每个独立打开的 tab 还会各自拉一次。代价是
  localStorage 跨会话持久，过期风险更大，所以版本号必须更严格。

  4. 如果要做，我建议的落地形态

  setNavbar 流程：
  1. 用 localStorage key = 'sitenav:' + 版本号（或直接 'sitenav.json?t=N' 全 URL）
  2. 命中 → 立即渲染（导航秒出，无 FOUC）
  3. 没命中 / 版本不符 → 发请求 → 写缓存 → 渲染
  4.（进阶可选）命中后后台再静默拉一次刷新 —— stale-while-revalidate，既秒开又不过期

  第 4 步那个「先渲染缓存、后台静默刷新」是最优解（首屏快 +
  最终一致），但会重新引入一个后台请求，就没法做到「完全不请求」了，属于「快」和「鲜」的折中。

  我的结论

  - 如果你的诉求只是「导航秒出、别闪空白」，那值得做，用 localStorage + 版本号 key，收益明确、成本可控；
  - 如果诉求是「省那点 304 流量/几十毫秒」，那收益太小，不值得为一个 sessionStorage 引入「过期导航」这种更难排查的
    bug。

  一句话：做可以，但版本号是硬前提，别只存不验。
